# Загрузка Qarzhy в GitHub

GitHub нужен для исходников и обновлений. Целевой репозиторий: https://github.com/bekasyl-karshygauly/qarzhy. Работающий сайт размещается отдельно на сервере с Node.js и PostgreSQL; GitHub Pages обслуживает статические страницы и не запускает API Qarzhy. [Результаты проверки](PUBLICATION.md) и [инструкция GitHub + Vercel](VERCEL.md).

## Перед первым пушем

1. Репозиторий уже предоставлен владельцем; проверка удалённых ссылок 22 октября 2026 не обнаружила веток или тегов. Проверьте видимость в GitHub, для начала предпочтителен приватный доступ. Пока не включайте GitHub Pages.
2. Откройте существующую папку `C:\Users\Admin\Documents\ChatGPT\finance` в GitHub Desktop или используйте Git из этой папки. Новый проект создавать не нужно.
3. Проверьте список файлов будущего коммита. Должны попасть `src`, `public`, `prisma`, `scripts`, конфигурация, документация и `package-lock.json`.
4. Не должны попасть заполненные `.env*`, `.local-db`, `.next`, `node_modules`, `.design`, `.superdesign`, `.vercel`, логи, дампы, резервные копии и приватные ключи. Правила исключения уже находятся в `.gitignore`. Безопасные `.env.example`, `.env.production.example` и `.env.vercel.example` добавлять можно. Выполните `npm run check:publish` и просмотрите состав коммита; проверка не заменяет полный аудит секретов и истории.
5. Сделайте первый коммит и push обычным способом. Не загружайте папку вручную через веб-интерфейс целиком: для такой загрузки `.gitignore` не фильтрует выбранные файлы автоматически.

Если секрет когда-либо попал в коммит, простого удаления файла в следующем коммите недостаточно: ключ нужно отозвать и заменить, затем очистить историю до публикации. В текущем локальном репозитории перед подготовкой не было отслеживаемых файлов или настроенного удалённого репозитория.

## После пуша

1. Для Vercel следуйте [VERCEL.md](VERCEL.md): облачная PostgreSQL, приватные env, отдельные миграции и первый аккаунт в закрытой среде. GitHub Actions уже подготовлен для CI; публикацию выполняет Vercel Git Integration после подключения владельцем. Она может запускаться независимо от CI, поэтому обязательные проверки настраиваются правилами ветки GitHub.
2. Для собственного сервера выберите домен и Node.js / Docker с PostgreSQL; регион и размещение данных проверяются отдельно по требованиям проекта.
3. Соберите приложение на целевой Linux-платформе. Локальную Windows-папку `.next/standalone` туда копировать не нужно.
4. Заполните `.env.production` приватно на сервере по `.env.production.example`: URL, пароль БД, сведения об операторе, при необходимости ключ Gemini. Не добавляйте заполненный файл в GitHub и не присылайте его в чат.
5. Настройте HTTPS и закрытый доступ для личного тестирования. Регистрация production-конфигурацией выключена. Существующий аккаунт требует отдельного переноса БД; при новой БД сначала нужно подготовить первый аккаунт в закрытой среде. Не включайте публичную регистрацию для обхода этого шага.
6. Выполните миграции и проверки из [DEPLOYMENT.md](DEPLOYMENT.md), проверьте вход, запись операции, перезапуск, резервную копию и восстановление. Контейнерный запуск ещё не проверен в этом Windows-окружении.

GitHub не является резервной копией пользовательских финансов: аккаунты и операции намеренно не входят в репозиторий.
