# Развёртывание

Загрузка исходников в GitHub описана в [GITHUB.md](GITHUB.md). Сам push не запускает Next.js и PostgreSQL. Шаблон настроек целевого сервера — `.env.production.example`; заполненный `.env.production` хранится вне репозитория.

Для размещения через GitHub + Vercel используйте отдельную [инструкцию](VERCEL.md) и [результаты проверки совместимости](PUBLICATION.md). Это сохраняет серверные функции; GitHub Pages для полной версии не подходит.

## Локальный тест (Windows)

Требуется Node.js 22.12+ (проверено на 24.21). Все команды выполняются из `qarzhy-mvp`.

```powershell
npm ci
npm run setup:local
npm run db:generate
npm run db:local
```

Оставьте терминал базы открытым. Во втором терминале:

```powershell
npm run db:migrate
npm run dev
```

Приложение: http://127.0.0.1:3100 . Используйте именно этот адрес: защита Origin сверяет его с APP_URL. Аккаунт нужно зарегистрировать самостоятельно. Готового пароля или демонстрационных финансовых данных нет.

`.env` создаётся со случайным паролем; не добавляйте его в Git. `.local-db` — настоящие данные PostgreSQL; не удаляйте её для обновления приложения. `Ctrl+C` в терминале базы корректно останавливает сервер. На Windows pg_ctl запускает сервер с ограниченным токеном; отдельная системная служба не устанавливается. Локальный PostgreSQL слушает только loopback.

Установщик создаёт UTF-8 базу. В текущем рабочем экземпляре используется `qarzhy_utf8` после исправления первоначальной кодировки; старую пустую базу сохранили. Нужный URL уже записан в `.env`.

Для собственной базы PostgreSQL 16+ задайте DATABASE_URL, затем выполните `npm run db:generate` и `npm run db:migrate`. Локальный помощник тогда не нужен. Для подключения вне хоста настройте TLS и проверку сертификата.

## Сборка и тесты

```powershell
npm run typecheck
npm test
npm run test:e2e
npm run build
npm start
```

Перед `npm start` остановите dev-сервер на том же порту. Playwright требует Chromium (`npx playwright install chromium` при отсутствии). Тесты регистрируют изолированные аккаунты `@example.invalid`, проверяют владение, CRUD, экспорт, удаление, повторный вход и мобильные размеры. Используйте тестовую базу. Для повторного применения ограничений после тестов не очищайте рабочие пользовательские данные.

## Сервер в Казахстане

1. Разместить приложение, PostgreSQL, резервные копии и журналы с персональными данными в Казахстане. Указать владельца/оператора и контакт в переменных и политике. Подтвердить регион документами хостинга.
2. Настроить HTTPS-прокси (Caddy/Nginx), APP_URL=https://ваш-домен, COOKIE_SECURE=true, ALLOW_REGISTRATION=false для закрытого пилота. Создать первый аккаунт в закрытом доступе, затем выключить регистрацию.
3. Отдельно задать случайный POSTGRES_PASSWORD (URL-safe), создать `.env.production` с параметрами приложения. Не копировать локальный `.env` в Docker-образ.
4. `docker compose --env-file .env.production up --build -d`. Compose применяет миграции до запуска приложения; база не публикует порт наружу. Установить POSTGRES_PASSWORD также в `.env.production` для интерполяции Compose.
5. Проверить `/api/health`, регистрацию в закрытом режиме, сохранение после перезапуска и восстановление из резервной копии. Docker в рабочем окружении отсутствовал: контейнерный запуск не проверен.
6. Выделить runtime-пользователя PostgreSQL с минимальными правами (SELECT/INSERT/UPDATE/DELETE), а DDL выполнять отдельной ролью миграций. Compose — стартовая конфигурация; она использует одну роль и требует разделения перед публичным запуском.
7. Планировщиком запускать `node --env-file=.env.production scripts/cleanup.mjs` ежедневно в среде с Prisma (например, migrate-образ): удаляет только истёкшие сессии и лимиты. Не удаляет финансовые данные.
8. Ввести зашифрованные резервные копии, ограниченный доступ, срок хранения и реестр удалений, чтобы восстановление не возвращало удалённые аккаунты. Например, целевой срок 30 дней должен быть согласован оператором и отражён в политике; он не настроен автоматически.

Production-образ проверяет наличие оператора, HTTPS, secure cookies и закрытой регистрации. Эта проверка не доказывает соблюдение закона. До публичного запуска добавить email-верификацию, восстановление пароля, антибот-защиту/WAF, аудит доступа, мониторинг, нагрузочное тестирование и процедуру реагирования на инциденты. Общие лимиты PostgreSQL защищают MVP, но не заменяют защиту на сетевом уровне.

## ИИ и голос

Текущий провайдер — Google Gemini через совместимый HTTPS endpoint `chat/completions` относительно AI_BASE_URL. Серверные переменные: AI_API_KEY, AI_MODEL, AI_PROVIDER_NAME, AI_PROCESSING_COUNTRY, AI_CONTEXT_MODE, AI_GOOGLE_PAID_SERVICES. Ключ никогда не имеет префикса NEXT_PUBLIC и не включается в клиентский код. Голос для Gemini не интегрирован и отложен по просьбе пользователя; VOICE_MODEL остаётся пустым.

Проверить договор, регион обработки, политику хранения, возможность удаления и основания трансграничной передачи. После настройки провайдера пользователь отдельно разрешает ИИ/аудио в настройках. При смене провайдера, URL или модели прежнее согласие перестаёт действовать. Без конфигурации API отвечает 503; без согласия — 403. Нет фальшивых ответов-заглушек.

Пользователь подтвердил бесплатный API Gemini: AI_CONTEXT_MODE=general, AI_GOOGLE_PAID_SERVICES=false. Сервер принудительно оставляет бесплатный/неподтверждённый Gemini в общем учебном режиме: после отдельного согласия передаётся только введённый вопрос, без чтения баланса, операций или месячных сумм. Вопрос не должен содержать личные или конфиденциальные сведения. История не отправляется; лимит — 15 вопросов в час на аккаунт. Финансовый контекст для другого подходящего провайдера требует отдельной проверки условий и согласия и сейчас не включён. Подробности — [GEMINI.md](GEMINI.md).

В текущей локальной установке пользователь приватно добавил ключ; реальный текстовый ответ Gemini через сервер и браузер проверен. Контракты отказа без настройки/согласия покрываются тестами. Квоты и доступность бесплатного провайдера меняются; настройки и работу нужно отдельно проверить на целевом сервере. Запись аудио не подключалась и не проверялась.
